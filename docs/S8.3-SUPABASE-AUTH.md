# S8.3 — Real Supabase Authentication & Security Architecture

## 1. Overview & Objective
Sprint **S8.3** transitions Knowra from prototype learner identification to **real, authoritative Supabase Authentication** using `@supabase/ssr` cookies and Row Level Security (RLS). 

All core Learning Engine mechanisms (Mastery, Confidence, Gap Engine, Next Best Action, Feynman evaluation, Review loop, AI Cache with pgvector, and Astra-first model strategy) remain intact.

## 2. Authentication Architecture

### Identity Flow
```text
Anonymous Visitor
       │
       ▼
Public Landing Page (/)
       │
       ▼ Click "Start Learning" / "Sign in"
Auth Modal / /auth
       │
       ├── Mode: SIGN_UP ──► supabase.auth.signUp({ email, password })
       └── Mode: SIGN_IN ──► supabase.auth.signInWithPassword({ email, password })
       │
       ▼
Supabase Auth Session established via secure HTTP cookies (@supabase/ssr)
       │
       ▼
Next.js Middleware validates session & permits access
       │
       ▼
Authenticated Learner Experience (/dashboard, /diagnostic, /map, /activity, /progress, /history)
```

### Components
1. **Browser Client** ([lib/db/supabase-browser.ts](file:///c:/Users/denio/Documents/Denio/EDUIA/lib/db/supabase-browser.ts)):
   - Initialized via `@supabase/ssr` `createBrowserClient(NEXT_PUBLIC_SUPABASE_URL, NEXT_PUBLIC_SUPABASE_ANON_KEY)`.
   - Automatically maintains session tokens and cookies across browser requests.
2. **Server Client** ([lib/db/supabase-server.ts](file:///c:/Users/denio/Documents/Denio/EDUIA/lib/db/supabase-server.ts)):
   - Initialized via `@supabase/ssr` `createServerClient` reading cookies via Next.js `cookies()`.
   - Validates session integrity on every server request.
3. **Identity Verification** ([lib/auth/get-user.ts](file:///c:/Users/denio/Documents/Denio/EDUIA/lib/auth/get-user.ts)):
   - Inspects `supabase.auth.getUser()` on every authenticated route.
   - Authoritative identity: if an active Supabase session exists, its `user.id` is returned unconditionally.
4. **Route Protection Middleware** ([middleware.ts](file:///c:/Users/denio/Documents/Denio/EDUIA/middleware.ts)):
   - Intercepts requests to private learner routes (`/diagnostic`, `/map`, `/activity`, `/progress`, `/history`).
   - Unauthenticated requests are automatically redirected to `/auth?redirect=<path>`.

## 3. Signup & Signin Flows

### Sign Up Flow
1. User provides valid email and password ($\ge 6$ characters).
2. Calls `supabase.auth.signUp({ email, password })`.
3. If email confirmation is required by Supabase project configuration, displays a notification advising the learner to verify their email before logging in.
4. If session is immediately established, automatically initializes a profile row in `public.profiles` (`id: user.id, email: user.email`).
5. Redirects to destination or dashboard.

### Sign In Flow
1. User provides credentials.
2. Calls `supabase.auth.signInWithPassword({ email, password })`.
3. Session cookies are written automatically by `@supabase/ssr`.
4. `useLearner` hook receives real-time auth change event (`SIGNED_IN`) and syncs user state.
5. Redirects to target destination.

### Sign Out Flow
1. User clicks "Sign Out" in Learner Navigation menu.
2. Calls `supabase.auth.signOut()`.
3. Clears client state and redirects to public landing page (`/`).

## 4. Audit & Elimination of Prototype Identity (`x-user-id`)

| Classification | Occurrences | Treatment in S8.3 |
| :--- | :--- | :--- |
| **A. Authentication / Security Identity** | `lib/auth/get-user.ts`, API routes | Replaced with `supabase.auth.getUser()`. Any header spoofing is strictly overridden by the authoritative session. |
| **B. Test-only Infrastructure** | Vitest test suites (`tests/*.test.ts`), validation scripts | Preserved strictly in offline test environments (`NODE_ENV === "test"` or `ALLOW_TEST_USER_HEADER === "true"`) when no Supabase session exists. |
| **C. UI State** | `useLearner.ts` | Refactored to listen to `supabase.auth.onAuthStateChange` and `supabase.auth.getUser()`. |
| **D. Arbitrary UI Switcher** | `learner-nav.tsx` | Removed prototype custom user ID input and demo switchers. Displays authenticated email and active session status. |

## 5. Security & Isolation Gates

### Impersonation Prevention Gate (Validated)
- **Scenario**: User A is authenticated via a legitimate Supabase session cookie, but sends `x-user-id: <User-B-UUID>` in request headers.
- **Enforcement**: [lib/auth/get-user.ts](file:///c:/Users/denio/Documents/Denio/EDUIA/lib/auth/get-user.ts) gives absolute priority to `supabase.auth.getUser()`.
- **Result**: The request operates strictly under User A's identity. User B's identity cannot be impersonated.

### Production Rejection Gate (Validated)
- **Scenario**: In production (`NODE_ENV === "production"`), an unauthenticated request attempts to pass `x-user-id`.
- **Enforcement**: Fallback header handling is restricted to non-production/test environments.
- **Result**: `getAuthenticatedUserId` returns `null`, triggering `401 Unauthorized`.

## 7. Remaining Limitations

2. **Password Reset**: Requires configuring transactional SMTP in Supabase project settings if "Forgot Password" is desired in a future sprint.
