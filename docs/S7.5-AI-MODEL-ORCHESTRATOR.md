# S7.5 — AI Model Orchestrator & Model Selection Layer Specification

## 1. Executive Summary & Architecture

The objective of Sprint 7.5 (S7.5) is to introduce an autonomous AI Model Orchestration layer between the Learning Engine and the AI Gateway, establishing model-agnostic operation across the EDUIA platform.

Target Architecture:
```
Learning Engine
      ↓
AI Task (Tutor, Feynman, Diagnostic, Assessment, etc.)
      ↓
AI MODEL ORCHESTRATOR
      ↓
MODEL SELECTION POLICY
      ↓
AI Gateway
      ↓
OpenRouter
      ↓
Selected Model (Astra / Claude / DeepSeek / GPT)
```

The Learning Engine remains completely unaware of:
- OpenRouter
- Model IDs
- Providers
- API credentials
- Routing rules
- Model pricing

The Learning Engine simply requests: *"I need a tutor explanation for this competency"* or *"Evaluate this Feynman submission"*, and the orchestrator handles model selection and operational resilience.

---

## 2. Difference Between Orchestrator and OpenRouter

- **OpenRouter (Provider Gateway)**: An external infrastructure abstraction providing a unified API protocol to access underlying LLM providers (Anthropic, OpenAI, DeepSeek, etc.).
- **AI Model Orchestrator (EDUIA Business/Technical Routing Layer)**: An internal routing layer that decides **which** model should execute a given pedagogical task based on task quality profiles, domain requirements, cost constraints, and operational fallback policies.

OpenRouter executes LLM calls. The EDUIA Orchestrator governs model decisions.

---

## 3. Model Registry & Environment Configuration

The Model Registry in `lib/ai/models.ts` is preserved and extended. Model configurations remain strictly environment-driven:
- `DEFAULT_MODEL`: Platform-wide default model candidate.
- Task-specific environment overrides:
  - `TUTOR_MODEL`: Tutoring and conversational explanations.
  - `FEYNMAN_MODEL`: Conceptual explanation evaluation and rubric scoring.
  - `CLASSIFIER_MODEL`: High-speed educational classification.
  - `DIAGNOSTIC_MODEL`: Diagnostic evaluation and baseline scoring.
  - `PLAN_MODEL`: Adaptive learning plan generation.
  - `COMPETENCY_MODEL`: Competency prerequisite reasoning.
  - `ASSESSMENT_MODEL`: Independent assessment generation.
  - `MATERIAL_MODEL`: Educational material and exercise generation.

---

## 4. Model Selection Policy

The model selection strategy follows a strict precedence:
1. **Task-Specific Override**: If a task-specific environment variable is set (e.g., `TUTOR_MODEL`), that model is selected.
   - Reason: `Task-specific environment override configured (${TASK}_MODEL)`
2. **Platform Default Candidate (`DEFAULT_MODEL`)**: If the task-specific variable is unset or empty, the orchestrator falls back to `DEFAULT_MODEL`.
   - Reason: `Resolved from DEFAULT_MODEL configuration` (or `Astra default candidate` if Astra is configured).
3. **Explicit Failure**: If both the task-specific variable and `DEFAULT_MODEL` are missing, the orchestrator throws an explicit error:
   `Model not configured for task: ${task}`
   **Invariant**: The system **never** silently guesses or selects an arbitrary model.

---

## 5. Astra Model Strategy

- Astra is designated as the primary/default model candidate for EDUIA.
- **Critical Invariant**: The codebase **never invents a fictitious model identifier**.
- Because an official Astra model identifier was not pre-existing in the repository configuration, `DEFAULT_MODEL` is kept configurable:
  ```env
  DEFAULT_MODEL=<exact-astra-model-identifier>
  ```
- When an Astra identifier is configured, the orchestrator automatically detects it, logs its candidate status in telemetry, and routes all un-overridden pedagogical tasks to Astra.

## 7. Cost & Latency Awareness (Quality > Cost)

In educational applications, pedagogical quality takes precedence over token cost:
- **Quality-Sensitive Tasks** (`Tutor`, `Feynman`, `Diagnostic`, `Assessment`, `Plan`, `Competency`):
  - Requirement: `qualityRequirement: "HIGH"`, `costSensitivity: "LOW"`
- **Cost-Sensitive Tasks** (`Classifier`):
  - Requirement: `qualityRequirement: "MEDIUM"`, `costSensitivity: "HIGH"`, `latencyRequirement: "LOW"`
- **Balanced Tasks** (`Material`):
  - Requirement: `qualityRequirement: "MEDIUM"`, `costSensitivity: "MEDIUM"`, `latencyRequirement: "MEDIUM"`

---

## 8. Operational Fallback Strategy

To ensure high availability without compromising academic rigor:
1. **Operational Failures**:
   - Triggers: HTTP 5xx, HTTP 502/503/504, HTTP 429 (rate limits), HTTP 404 (endpoint unavailable), network timeouts, connection refused.
   - Action: If `FALLBACK_MODEL` or operational fallback is configured, the orchestrator automatically re-routes the prompt to the fallback model.
   - Telemetry: Records `fallbackUsed: true`, `fallbackModel`, and `fallbackReason`.
2. **Business / Schema Failures**:
   - Triggers: Zod schema validation errors, JSON parse errors.
   - Action: **NO FALLBACK**. Re-throws the schema error immediately.
   - Invariant: Operational fallback never masks hallucination or schema non-compliance.

## 9. Telemetry & Model Observability

Every AI invocation records:
- `operation`: e.g. `generateText:classifier`, `generateStructured:feynman`
- `task`: normalized task identifier
- `provider`: e.g. `openrouter`
- `model`: actual model that generated the completion
- `promptTokens`, `completionTokens`, `totalTokens`
- `latencyMs`
- `estimatedCost`: computed per million tokens
- `status`: `SUCCESS`, `FAILED`, or `SCHEMA_ERROR`
- `orchestrationPolicy`: policy version (`EDUIA_POLICY_V1`)
- `selectionReason`: why the model was chosen
- `fallbackUsed`, `fallbackModel`, `fallbackReason`

### Model Observability API
The `TelemetryService.getModelObservabilityStats()` aggregates usage by `model:task`:
- Call count
- Success count & failure count
- Schema error count
- Total tokens & total cost
- Average latency in milliseconds
- Fallback invocation count

## 10. Future Model Benchmarking & Evaluation

`lib/ai/evaluation.ts` provides a benchmarking harness:
- `benchmarkModel(modelId, context)`: Evaluates a single model against a test prompt/schema, measuring latency, cost, and validity.
- `compareModels(modelIds, context)`: Runs head-to-head empirical comparisons between candidate models (e.g., Astra vs Claude vs DeepSeek vs GPT) and produces structured comparison reports.

---

## 11. Security & Secrets Management
- All OpenRouter API keys and Supabase credentials remain strictly server-side.
- Zero client-side leakage.
- Clean separation between business logic and credentials.
